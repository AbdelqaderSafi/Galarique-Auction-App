# GalleryQ / Gallerique — Backend Project Context

Art & collectibles **auctions** mobile app (graduation project). This repo is the **entire backend**; a separate team builds the Flutter/mobile app in parallel against the deployed API. Brand tagline: "Bid Smart. Win Big."

- **Stack:** NestJS 11 · Prisma 7 · PostgreSQL · TypeScript.
- **Deployed:** API on **Railway**, DB on **Neon**. Base URL: `https://galarique-auction-app-production.up.railway.app` · Swagger: `/api/docs`.
- **Source of truth for data model:** `prisma/schema.prisma`. Full analysis: `docs/ANALYSIS.md`. Design decisions: `docs/design/specs/2026-06-21-backend-clarifications-design.md`.

---

## Code conventions (follow these exactly — match existing modules)

- **Prisma access:** inject `DatabaseService` (extends `PrismaClient`, provided by the `@Global() DatabaseModule`) — conventionally named `prisma`. Do NOT import a new PrismaClient.
- **Types/enums:** import from `generated/prisma/client` (custom generator output at `generated/prisma`), e.g. `import { Role } from 'generated/prisma/client'`.
- **Validation:** Zod schema per module in `src/modules/<m>/util/<m>.validation.schema.ts`, applied with `ZodValidationPipe` (`src/pipes/zod.validation.pipe.ts`) on the `@Body()`.
- **DTOs:** request DTOs are **classes** with `@ApiProperty` in `src/modules/<m>/dto/<m>.dto.ts`; response shapes are exported `type`s.
- **Swagger:** extract endpoint decorators into `src/swagger/<m>.swagger.ts` using `applyDecorators(...)` (see `src/swagger/auth.swagger.ts` / `categories.swagger.ts`). Tag with a `SwaggerXTag()` helper.
- **Module shape:** `@Module({ controllers, providers, exports })`; register the module in `src/app.module.ts` `imports`.
- **Auth is global:** `AuthGuard` + `RolesGuard` are registered as `APP_GUARD` in `AuthModule`, so **every route is protected by default**.
  - Open a route with `@IsPublic(true)` (`src/decorators/public.decorator.ts`).
  - Restrict by role with `@Roles([Role.ADMIN])` (`src/decorators/roles.decorator.ts`). `req.user` is the user without password (includes `roles`).
- **Passwords:** hashed with **argon2**. **JWT** via `@nestjs/jwt`, payload `{ sub, roles }`, 30-day expiry.
- **Money:** always `Decimal(12,2)` in Prisma (never Float). Currency is **USD** only.
- **main.ts:** `app.enableCors()`, listen on `process.env.PORT ?? 3000` bound to `0.0.0.0`, Swagger mounted at `api/docs`.
- **Per-module workflow:** agree scope → build (DTO+Zod+service+controller+swagger+module, register in app.module) → `tsc`+`nest build` → boot and test EVERY endpoint (happy path + auth/role/validation) → commit (user decides push).

## Domain model & product decisions (agreed — do not re-litigate)

**Scope:** Only the Figma page `buyer flow AI` is approved (it holds both buyer & seller screens). **Shipping is OUT of scope.** No saved cards, no in-app chat, no in-app notifications, no separate EXPERT role, no multi-currency.

**Object vs Auction:** `Object` = the artwork (owner, `category` **enum**, title, required `mainImage` (cover), optional description/era/condition/originality/dimensions, up-to-10 additional `images`, status). `Auction` = a timed event on an Object. **The whole thing is created in one request** (`POST /auctions`) that runs the Figma wizard end-to-end: Category → Images → Details → Set Value → Duration → Review — it creates the `Object` **and** the `Auction` together in one transaction. There is **no standalone objects module** (it was removed; the `Object` model stays for ownership/favorites). Set Value collects only `startingPrice` (= min-to-sell) — **`reservePrice` was dropped entirely** (no column) and **no `estimatedValue`** (also dropped from the model).

**`minBidIncrement` is tiered by price — the seller never sets it (fixed at $10 on 2026-08-05, made tiered on 2026-08-06).** It was removed from the `POST /auctions` and `PATCH /auctions/:id` schemas (a client that still sends it has the value silently stripped by Zod). The increment now follows the **current price** through a fixed table in `src/modules/auctions/util/bid-increment.util.ts`:

| نطاق السعر الحالي ($) | الحد الأدنى للزيادة ($) |
|---|---|
| أقل من 25 | 1 |
| 25 – 100 | 2 |
| 100 – 1,000 | 10 |
| 1,000 فأكثر | 50 |

Boundaries are **closed at the bottom** — exactly 100 → the $10 tier, exactly 1000 → the $50 tier. `minIncrementFor(price)` is the **single source of truth**; the `Auction.minBidIncrement` column is only a **read-side copy** the backend rewrites on every price change (seeded from `startingPrice` at create, re-seeded in `PATCH` if `startingPrice` changes, rewritten in `BidsService.place()` from the new price). `BidsService` validates against the function and **never** reads the column, so a stale column can't corrupt a bid. The helper lives under `auctions` (not `bids`) because `bids` already imports from `auctions` (`PUBLIC_STATUSES`) — the reverse would be circular. Migration `20260806090000_tiered_bid_increment` realigned **all** existing rows to the table (49 rows, 35 changed; only 3 were LIVE and none of those had bids yet). Responses still carry `minBidIncrement` per auction — and because it now changes as the price crosses a boundary, the mobile app must **re-read it** rather than caching it once: the `bid` SSE event and the `POST /auctions/:id/bids` response both carry the updated value.

**Seller-defined custom fields (built 2026-08-05):** on top of the fixed Details fields, the seller can add up to **5** extra fields they name themselves — `Object.customFields` is a `Json @default("[]")` column holding `[{ label, value }]` (both plain text; `label` ≤ 30 chars, `value` ≤ 120 chars, trimmed, non-empty, labels unique case-insensitively). Because it is a scalar on `Object` it is returned automatically by **every** existing read (`GET /auctions`, `/auctions/:id`, `/auctions/mine`, `/auctions/seller/:sellerId`, the admin queue) — no `include` changes. It is **never `null`** — the column is NOT NULL and the migration backfilled existing rows with `[]`. Transport differs by endpoint and one shared Zod schema (`customFieldsSchema`) accepts both: `POST /auctions` is multipart so it arrives as a **JSON string** (`customFields=[{"label":"Artist","value":"Van Gogh"}]`, malformed JSON → 400 `customFields must be a valid JSON array`), while `PATCH /auctions/:id` takes a real **array**. Edits are **replace-all**, exactly like `images`: send an array → replaces, send `[]` → clears, omit → unchanged.

**Categories:** a fixed **enum** `Category` (`ART, WATCHES, COLLECTIBLES, JEWELRY, FURNITURE, BOOKS, FASHION, ELECTRONICS`) — NOT a table. `GET /categories` (public) returns the `{ value, label }` list.

**Auction lifecycle:** `DRAFT` (Save-as-Draft) →(submit)→ `PENDING_REVIEW` → **ADMIN approves** → `LIVE` (`startTime=now`, `endTime=now+durationDays`) → `ENDED` → `SOLD`/`UNSOLD`; or ADMIN `REJECTED` (+`rejectionReason`, seller edits → auto-resubmits to PENDING, or cancels). Creating with `saveAsDraft:true` yields `DRAFT`; otherwise it goes straight to `PENDING_REVIEW`. Seller picks a **preset `durationDays`** — **1/3/7/10** (from the Figma Duration screen; end date/time itself is ignored, only the day count matters). Anti-snipe: a bid within `antiSnipeSeconds` (default 60) of `endTime` extends it by `extendBySeconds` (default 60).

**Bidding (built — see the `bids` module):** free amount; the **first** bid in an auction must be `≥ startingPrice`, every later bid `≥ currentPrice + minIncrementFor(currentPrice)` (the tier of the price being raised **from**, not of the new bid). The whole bid runs in one **interactive DB transaction** that starts by row-locking the auction (`SELECT ... FOR UPDATE`) for concurrency.

**Deposit model (decided 2026-07-15 — supersedes the older "held until close" rule):** a **flat $50 deposit** is held on **whoever is the current highest bidder**, and **released the moment they are outbid**:
- Taking the lead → `balance → lockedBalance`, `AuctionDeposit` → HELD, `WalletTransaction` DEPOSIT_HOLD.
- Being outbid → `lockedBalance → balance`, `AuctionDeposit` → RELEASED, `WalletTransaction` DEPOSIT_RELEASE (immediately, inside the same transaction as the new bid).

So at close **only the winner still holds a deposit** — there are no held "losers" to release later. One `AuctionDeposit` row per `(auctionId, userId)` (`@@unique`), toggled `HELD ↔ RELEASED` (a bidder who retakes the lead re-holds on the same row). "You pay only if you win."

**Winning & payment (built — see the `scheduler` + `orders` modules, decided/built 2026-07-16):** a `@Cron(EVERY_MINUTE)` job (plus an ADMIN manual trigger, `POST /scheduler/run`) runs three idempotent "scan for due work" jobs — closing due auctions, expiring payment deadlines, retrying pending winner payments — each a row-locked transaction that re-checks state after acquiring the lock, so a missed tick or two overlapping instances can never double-process the same row. On close: no bids → `UNSOLD` (Object → `AVAILABLE`); a winner → `ENDED` + an `Order` (`offerRank=1`, `amount=currentPrice`, `depositApplied=50`, `amountDue=max(0, amount-50)`, `paymentDeadline=+72h`), then an immediate payment attempt. **`payOrder()` is the single payment path** used by all three callers (auto-deduct at close, `POST /orders/:id/pay`, and the scheduler's auto-retry job) — atomic guarded debit, deposit `HELD→APPLIED`, any excess where price < $50 refunded to the buyer, seller credited the **full price immediately** (no escrow). Unpaid within 72h → **$50 deposit FORFEITED**, order `DEFAULTED`, and the auction is offered to the **second-highest bidder** at ***their own bid price*** — **optional, never auto-charged** (`retryWinnerPayments` only ever touches `offerRank=1`), `depositApplied=0` (their deposit was already released when they were outbid). If that lapses too → order `CANCELLED` (no deposit to forfeit), auction `UNSOLD`, Object back to `AVAILABLE`. No cascade past the second bidder.

**Escrow and disputes were REMOVED from the product (decided 2026-07-16).** Payment credits the seller's wallet **immediately** — no holding period, no "confirm receipt", no 14-day auto-release, no `disputes` module. **Accepted consequence: the buyer has no in-app protection** if a seller takes payment and never hands over the item — a deliberate scope reduction for a graduation project, not an oversight. `OrderStatus.PAID_IN_ESCROW`/`DISPUTED`/`REFUNDED`, `Order.autoReleaseAt`, `WalletTxnType.ESCROW_IN`/`ESCROW_RELEASE`, and the `Dispute`/`DisputeStatus` models are **dead but retained in the schema** (removing them would trigger the migration-drift/reset gotcha for zero benefit — see Gotchas).

**Wallet:** `balance` (available/withdrawable) + `lockedBalance` (pending $50 deposits). Every movement logged in `WalletTransaction` (`PURCHASE`/`SALE` added for order settlement — see below).

**Payments (Stripe, USD) — wallet module built:** wallet **top-up** = Stripe **Checkout + webhook** (the server creates a Checkout Session via `POST /wallet/topup` and returns `checkoutUrl`; Stripe hosts the payment page). **Confirmation is webhook-only** (`POST /wallet/stripe/webhook`, `@IsPublic`): verify the signature with `STRIPE_WEBHOOK_SECRET`, on `checkout.session.completed` (`payment_status:"paid"`) credit `balance` + log a `TOPUP` `WalletTransaction`. **Idempotent** via a unique `WalletTransaction.stripeEventId` column (duplicate event → Prisma P2002 → skip; credit + insert share one DB transaction). (Switched from PaymentIntent → Checkout.) **Withdrawal** = **Stripe Connect Express, synchronous Transfer**: `POST /wallet/connect/onboard` (create Express account + onboarding link) → `GET /wallet/connect/status` (charges/payouts enabled) → `POST /wallet/withdraw` (guarded atomic debit, then `stripe.transfers.create` to the connected account; PAID+`stripePayoutId` on success, FAILED+refund on error) via the `Withdrawal` model + `WithdrawalStatus`. **Any authenticated user** can onboard/withdraw. Limits: amount > 0 (≤ 2 dp), withdraw ≤ balance. Uses `stripeConnectId` on User (`stripeCustomerId` unused with Checkout). **No saved cards.** Raw body for signature verification wired via `NestFactory.create(AppModule, { rawBody: true })` in `main.ts` (keeps JSON parsing for every other route). `StripeService` is resilient — throws `503` if `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` missing. `STRIPE_SECRET_KEY` + `STRIPE_WEBHOOK_SECRET` live in the backend only (test keys in `.env`; webhook secret from `stripe listen` locally).

**Seller verification = phone OTP over WhatsApp (built):** any authenticated user submits a **Palestinian** phone (`+970`/`+972`, mobile prefix 59/56) → `POST /seller/request-verification` → 6-digit OTP sent via **WhatsApp (Baileys 6.7.x, free, unofficial)** → `POST /seller/verify-phone` creates `SellerProfile` (`phoneNumber`, `phoneVerifiedAt`) and **grants the `SELLER` role**. Also `POST /seller/resend` and `GET /seller/whatsapp/status` (ADMIN). The `whatsapp` module (`@Global`) loads Baileys via dynamic `import()` (ESM) and is **resilient** — if WhatsApp isn't linked it logs the code to the console. Link via **pairing code** (`WHATSAPP_PAIRING_NUMBER`) or QR; session persists to `./wa-auth` (gitignored; needs a Railway Volume to survive redeploys). Uses the existing `PhoneVerification` model. (Firebase SMS was built then dropped because it's paid.) **`SELLER_OTP_SIMULATE`** (env): when enabled, `request-verification`/`resend` **return the OTP in the response** and skip WhatsApp entirely — lets you become a SELLER end-to-end without a linked WhatsApp session (dev/testing only; never enable in production).

**Images (built):** the `uploads` module receives files (multer) and uploads to **ImageKit** (`IMAGEKIT_PUBLIC_KEY` / `IMAGEKIT_PRIVATE_KEY` / `IMAGEKIT_URL_ENDPOINT`), stores the returned URL. **`POST /auctions` is `multipart/form-data`**: it takes the actual image files from the device (`mainImage` single file + `images` up to 10) and uploads them to ImageKit internally (via `UploadsService`), then stores the URLs — no separate upload step. The standalone `/uploads` endpoints still exist (used by `PATCH /auctions/:id`, which takes image **URLs**).

**Notifications (built as `mail`):** **email only** via **Brevo HTTP API** (`BREVO_API_KEY`, `MAIL_FROM`; sender must be a Brevo *verified sender*). The `MailService` is resilient — logs the content if the key is missing (and logs nothing on a successful send). Wired: auction approved/rejected (`auctions`); **outbid** (`bids` — `sendOutbid`); **payment required, order paid, item sold, second chance, auction unsold** (`orders`/`scheduler` — `sendPaymentRequired`/`sendOrderPaid`/`sendItemSold`/`sendSecondChance`/`sendAuctionUnsold`). All fire post-commit, fire-and-forget, so a mail failure can never fail the underlying transaction. Buyer↔seller contact is via `mailto:` (no chat) — `GET /orders/:id` returns the counterpart's email for exactly this. **Following a seller does NOT send any notification** — no "seller published a new auction" email/push exists; `follows` is purely a stored relationship for the "Fav Sellers" list.

**Real-time bid updates (built 2026-07-21 — see the `realtime` module, SSE not WebSocket):** an isolated `RealtimeModule` with an in-memory `Map<id, Subject<MessageEvent>>` pub/sub (one channel per auction, one per user) exposes two `@Sse()` streams — `GET /auctions/:id/stream` (🔒, 404 unless the auction is in a **public** status) broadcasts `bid` (new price/bidder/endTime, reflecting any anti-snipe extension, **plus the new `minBidIncrement`** — the tier changes when the price crosses 25/100/1000, so a listener must not cache it) and `closed` (ENDED/UNSOLD + winner) events; `GET /me/stream` (🔒) is a personal channel for `outbid` and `won` (payment-required) events. `BidsService.place()` and `SettlementService.closeDueAuctions()` call `RealtimeService.publish*()` as `void` fire-and-forget calls **after** their transaction commits — a broadcast failure can never fail a bid or a close. **One-directional only** (bidding stays REST `POST /auctions/:id/bids`); no event replay (reconnect resyncs via the existing REST reads — `GET /auctions/:id` + `GET /auctions/:id/bids`); no Redis (single-instance in-memory `Subject`s — the documented future path if ever needed, not built). A ~25s keepalive ping prevents Railway's proxy from cutting idle connections. Design: `docs/design/specs/2026-07-21-realtime-bids-sse-design.md`; plan: `docs/design/plans/2026-07-21-realtime-bids-sse.md`.

**Guest:** browse only; bidding/following/favoriting require auth. **Favorites:** `FavoriteAuction` (auctions-only by product decision, see `favorites` module below) and `Follow` (= Fav Sellers). `FavoriteObject` exists in the schema but is dead/unused (no API surface).

**Account settings (built 2026-07-25 — see the `user` module):** `PATCH /users/me` (🔒 any authenticated user) partially updates `username` (unique, 3-30 chars, letters/digits/`_`/`.`; 409 if taken), `dateOfBirth` (must not be in the future), and/or `phoneNumber` (format-checked only — **no OTP/verification**, unrelated to the seller-verification phone on `SellerProfile`). At least one field required per call; all three are nullable on `User` and `null` until the user sets them. This is a deliberately narrow scope from the Figma "Account settings" screen — **out of scope on purpose:** splitting `fullName` into first/last name, changing the email, and "Delete my account" (none built; `fullName`/`email` update stays unavailable). The "Address" (shipping/billing) screen is not built at all — shipping is out of scope for the whole product.

**Auth (built, full):** `register` does NOT create the user immediately — it emails a 6-digit code and stores the pending signup in the `EmailVerification` model; `verify-email` checks the code and only THEN creates the `User` + issues a JWT. Also: `resend-verification`, `login`, `google`, `validate` (🔒, renews the JWT + returns the user), `forgot-password` (emails a **6-digit code** stored in the `PasswordReset` table; generic response — no user enumeration), `reset-password` (`{ email, code, newPassword }`), `change-password` (🔒, needs current password). OTP settings from `OTP_EXP_MINUTES` / `OTP_MAX_ATTEMPTS`. (Password reset is code-based in-app, NOT a link.)

**Admin:** no separate login — everyone uses `POST /auth/login`; `roles` containing `ADMIN` gates `@Roles([ADMIN])`. Public `register` always creates `[BUYER]`. Admins are created by **`npm run seed`** (`prisma/seed.ts`, uses raw `pg` + argon2 — NOT the Prisma client, see gotcha) from `ADMIN_EMAIL`/`ADMIN_PASSWORD`/`ADMIN_FULLNAME`.

## Modules

**Built:** `auth` (full — see above), `user` (profile settings — `PATCH /users/me` for `username`/`dateOfBirth`/`phoneNumber`, all optional/partial, no verification; see Account settings below), `database` (`@Global`), `mail` (Brevo), `uploads` (ImageKit), `whatsapp` (`@Global`, Baileys), `seller-verification` (WhatsApp OTP → SELLER), `categories` (GET public — fixed enum list), `auctions` (unified wizard — creates Object + Auction in one `POST`; draft/submit/edit/delete/cancel; admin review queue + approve/reject; public browse/detail; approve/reject emails), `wallet` (balance/lockedBalance + ledger; Stripe **Checkout** top-up + **webhook**; Stripe **Connect Express** onboarding/status + **synchronous withdrawal Transfer**), `bids` (place bid in a row-locked transaction; $50 deposit hold + **release-on-outbid**; anti-snipe; outbid email; public bid history + my-bids), `orders` (the `Order` lifecycle — `payOrder()` single payment path, reads, settlement emails), `scheduler` (cron-driven auction close + payment settlement — see Winning & payment above), `favorites` (built 2026-07-20 — `FavoritesController`/`FollowsController` in one `favorites` module: favorite **auctions only** + follow sellers, all idempotent add/remove + paginated lists), `realtime` (built 2026-07-21 — SSE auction + personal streams, see Real-time bid updates above). **The standalone `objects` module was removed** — object CRUD now lives entirely inside `auctions`. **The planned `disputes` module was dropped** along with escrow (see Winning & payment).

**Roadmap: fully complete** — every planned module (including real-time bid updates) is built. Only the refresh-tokens decision below is open, and it's optional/deferred pending mobile-team coordination.

**Schema note:** `EmailVerification` (pending signups), `PhoneVerification` (seller OTP), and `PasswordReset` (password-reset OTP) are OTP tables (codeHash/expiresAt/attempts/consumedAt); `SellerProfile` is phone-based (`phoneNumber` unique + `phoneVerifiedAt`); `User` has `stripeCustomerId`/`stripeConnectId`; `Object.category` is a `Category` enum column and `Object.description` is **nullable**; `Auction` has no `estimatedValue` and no `reservePrice` (both dropped — `startingPrice` is the min-to-sell). `WalletTxnType` gained `PURCHASE`/`SALE`; `DepositStatus` gained `APPLIED` (2026-07-16, additive migration) for order settlement. `User` gained nullable `username` (unique)/`dateOfBirth`/`phoneNumber` (2026-07-25, additive migration) for account settings — see Account settings above. `Object` gained `customFields Json @default("[]")` and `Auction.minBidIncrement`'s default moved `50 → 10` (2026-08-05, migration `20260805120000_fixed_bid_increment_and_custom_fields` — both additive). Then `20260806090000_tiered_bid_increment` (2026-08-06) made the increment **tiered** — a **data-only** migration (no schema change) that realigned every existing row to the tier table; the `@default(10)` is now just a fallback the service always overwrites — see the tiered-increment and custom-fields notes above.

## Gotchas (important)

- **Build entry is `dist/src/main.js`** (not `dist/main.js`) because `prisma.config.ts` at the repo root lifts the tsc rootDir. `start:prod` and `railway.json` already point there.
- **The generated Prisma client uses `.js` ESM import specifiers**, which `ts-node` cannot resolve — so **`prisma/seed.ts` uses raw `pg` + argon2**, not the Prisma client. At runtime `nest build` emits relative `require`s, so the app works. Keep this in mind for any script run via ts-node.
- **`prisma migrate dev` refuses to run non-interactively when it has warnings** (enum value removal, dropping a table, new unique constraints). In an interactive terminal it prompts and works. Headless fallback: `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script --output <dir>/migration.sql`, then `prisma migrate deploy`. (Watch statement ordering when a table and enum share a name — drop the table before creating the enum.)
- **Neon SSL:** `pg` prints a non-blocking `sslmode` warning; `channel_binding=require` in the URL is harmless (pg ignores it) — remove it only if you hit a SCRAM/auth error. `sslmode=require` is required. Neon scales to zero — the first request after idle may cold-start / a migrate may need a retry.
- **Baileys is ESM-only** (`"type": "module"`) while this project is CommonJS — load it with dynamic `await import('@whiskeysockets/baileys')` (never a static import; `module: nodenext` preserves `import()`). Use **stable 6.7.x** (the 7.0.0-rc pairing was broken). `WhatsappService` starts on `onModuleInit` without blocking boot and falls back to console logging when not linked.
- **Pre-existing migration drift:** `20260706160744_category_enum` was edited after being applied, so `prisma migrate dev` reports "modified after applied" and wants to **reset the DB** (would wipe the mobile team's data — never do this). `migrate status` still says "up to date". Workaround for new migrations: generate SQL with `prisma migrate diff --from-config-datasource prisma.config.ts --to-schema prisma/schema.prisma --script`, drop it into a new `prisma/migrations/<ts>_<name>/migration.sql`, then apply with **`prisma migrate deploy`** (which never resets) + `prisma generate`. This is how `20260709145120_wallet_txn_stripe_event_id` was applied.
- **`ZodValidationPipe` + `@UsePipes` is a trap on routes with path params.** The pipe (`src/pipes/zod.validation.pipe.ts`) does **not** check `metadata.type`, so it validates **every** handler parameter. Applied via method-level `@UsePipes(new ZodValidationPipe(schema))` on a handler that also has `@Param('id')`, it runs the body schema against the **id string** → every request 400s with `"expected object, received string"`. It compiles fine and only fails at runtime. `wallet` gets away with `@UsePipes` because its handlers have no path param. **Always apply it inline on the body — `@Body(new ZodValidationPipe(schema)) dto: X`** — as `auctions` and `bids` do. (This bit the `bids` controller; fixed in `439be45`.)
- **Testing a time-based flow:** `Auction.endTime` is a Prisma `DateTime` → Postgres `timestamp` **without** time zone. The app (Prisma) reads it back as **UTC**, consistent with `new Date()`, so the `endTime <= now` check is correct. But a throwaway script using raw `pg` parses that naive timestamp in the **process's local zone** (UTC+3 here), so the same row can look ~3h off between a `pg` script and the API's JSON. Compare before/after through **one** client, or the offset will look like a bug that isn't.
- **`"Order"` is a reserved SQL keyword** — any raw query touching that table (e.g. the `SELECT ... FOR UPDATE` row lock in `payOrder`/`SettlementService`) must keep it double-quoted, or Postgres parses it as the `ORDER BY` keyword instead of a table name.
- **The scheduler cron runs for real, independently of any manual trigger.** `@Cron(EVERY_MINUTE)` fires on its own the whole time the app is up (dev included) — while testing `POST /scheduler/run` manually, the background tick can race ahead and settle the same due rows first, so a manual tick's returned `{closed, expired, retriedPaid}` counts can legitimately read `0` even though the work already happened. This was observed live and is by design (the scan-then-lock-then-recheck pattern makes it safe either way) — assert on the resulting *state*, not on which specific tick call reported the count.
- **Stripe raw body:** the webhook needs the raw request bytes for signature verification — enabled globally via `NestFactory.create(AppModule, { rawBody: true })` (read in the controller with `@Req() req: RawBodyRequest<Request>` → `req.rawBody`). This keeps normal JSON parsing for all other routes; do **not** remove the `rawBody` option or the webhook signature check breaks.
- Never commit `.env` (Neon URL w/ password, JWT secret, **Stripe secret/webhook keys**, etc.) or `wa-auth/` (WhatsApp session) — both are gitignored.
